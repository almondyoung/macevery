# MacEvery 第三轮查询 CPU 与增量刷新优化

日期：2026-10-18；版本：r2，本轮本地优化、安装及限定验收完成。

基线为第二轮已安装源码及文档主干 `ec58990b217d10d0c9b3e5b77e8ebe1c36d4a3e9`。用户授权验证通过后替换本机 App、提交和推送。保留 0.1.3，以 Git SHA 标识开发构建；不创建正式 release/tag。

## 实现

- 查询预编译长词查找及 glob 的必要字面量，长词查找设线性回退，避免病态输入反复回溯。纯通配符及单字面量有快捷路径；保留原有字节匹配语义、分数及首个匹配位置。
- kind/ext/mtime 提前过滤；packed 扫描只读取需要的小写片段，Top-K 先比较分数、时间和路径长度，仅在需要时读取原路径。全部结果字段与稳定排序保持。
- SQLite 文件变更触发器在同一事务中记录 revision、旧/新 ID 及 OR REPLACE 隐式冲突删除的 ID。控制元数据（meta/roots/excludes/checkpoint）、no-op 与回滚不产生已提交文件变更；size/mtime 等文件元数据实际变化会记录。主键改变、删除再插入/复用 ID、外部 SQL 写入均有回归。
- 增量读取在一个 WAL 读快照中检查 revision 连续性并获取最终记录；每次最多 4,096 个事件/ID，字符串及 kind 解析的保守载荷预算为 32 MiB，复制前检查。它是逻辑载荷上限，不代表服务总内存上限。日志保留 16,384 条，加至多 1,023 条裁剪尾部，避免无限增长。
- packed 原槽修改、墓碑删除、递增 ID 追加，不创建全量 ID Map。元数据变更不分配新字符串。死字符串 32 MiB、死记录数量阈值及新增扩展字典 4 MiB 触发完整整理；缺失的低位新 ID 也安全回退。
- 仅在读事务和全部应用成功后公布新 stamp。读取失败返回 503，应用异常丢弃可能部分修改的索引后重试；日志缺失/断档、超过预算、数据库替换与整理需求回退到一致快照全量加载。显式 `/reload` 仍强制完整加载。

## 正确性

- Debug/Release 各 100 项 library tests，以及固定种子的 420 次混合事务集成测试通过；12 类操作各 35 次，396 次增量应用（326 次含实际变更）、24 次安全回退。每个事务将完整 FileRecord 和九类查询与同一数据库快照的新建 packed/完整记录搜索比较。
- 独立保留旧 scorer/glob/filter 作为 oracle，覆盖 Unicode、字节通配符、长词病态输入、空值、稳定同键排序、分块边界和碎片预检。交叉源码复核未发现阻断问题。
- 覆盖快照期间后续提交、并发仅一次应用、日志裁剪/缺失/事件与 ID 超限、失败恢复、OR REPLACE、事务回滚及无效 UTF-8/超长 kind 的载荷限制。
- 严格 Clippy all-targets、格式/diff、Python 语法及 Swift GUI 回归通过。GUI 取消、CLI 子进程回收、重试和背压行为沿用第二轮。
- 初次集成的一个故障夹具因 schema 刻意删除/恢复后未重新打开外部 writer 而失败，已修正并通过完整回归；原始失败保留。独立复核补充 kind 临时 lowercase 预算后，重新冻结制品并复跑最终测试及基准。

## HTTP 文件更新与回退

使用同一迁移后的冻结索引副本，A→B 顺序启动独立、带认证的 loopback memory 服务；每批修改 1,000 条普通记录，并执行探针重命名、删除/插入及主键变更。CPU 仅计服务进程，控制器写库与数据准备不计入测量窗。

wave 1/2 的变更及首次查询相同，可比较完整刷新与增量刷新。候选额外执行窗外 `/status` 验证 stale 且不刷新；此为单次机制比较、暖缓存观测，不能替代重复延迟统计。wave 3 包含 40 个搜索和循环 health/status，成功/503 数量可能不同，仅作为正确性、并发与背压证据，不以 CPU/40 宣称查询加速。

两个服务全部通过，所有指定阶段完整 JSON 一致；三批普通变更的候选 full reload 为 0、incremental applies 为 1/2/3，对应 1,002/1,003/1,002 个最终变化 ID。

| 变更后首次查询 | 第二轮 CPU | 第三轮 CPU | 第二轮耗时 | 第三轮耗时 |
| --- | ---: | ---: | ---: | ---: |
| 第 1 批 | 4.570 秒 | 0.0207 秒 | 15.311 秒 | 0.0212 秒 |
| 第 2 批（含主键变化） | 4.578 秒 | 0.0237 秒 | 15.302 秒 | 0.0240 秒 |

这两次服务 CPU 分别降低 99.55%/99.48%。仅代表上述有界变更及 ext 探针查询，不代表任意大批量变更或所有实际查询耗时。普通三批后 packed 分配容量基本不变。整个含故障回退的服务生命周期 RSS 峰值为旧版 2.611 GiB、新版 2.639 GiB（约 +1.1%），没有进一步下降；主内存比较仍以前述固定查询 A/B/A 为准。

40 并发中两版本均为 2 个正确 200、38 个明确 busy 503；每个 200 的完整 JSON 及两版本之间全部一致，health/status 均 200 且与搜索窗口重叠，自有进程组和端口均已回收。控制请求次数随时间不同，不比较本阶段总 CPU。

显式 reload 仍需约 4.50/4.64 秒 CPU；4,097 个事件超限回退约 4.59/4.72 秒 CPU（旧/新），完整加载本身没有获得本轮提速。日志断档、缺失自动修复以及读取失败 503/恢复均通过。

显式 reload、事件超限、日志断档/删除及读取失败恢复另行验证。阶段 20 ms RSS 为采样下界；wait4 生命周期峰值覆盖启动及全部故障阶段；packed 容量不是 RSS。HTTP 对 SQLite 核对输出字段 path/basename/kind/size/mtime，A/B 全 JSON 比较还覆盖 score/排序；HTTP 未输出字段由 Rust 完整记录差分覆盖。

30 万条受控索引的真实 FSEvents A/B/A 也通过：创建、修改、文件/目录重命名和删除、排除目录写入风暴及后续更新共九类检查，最终状态一致。watch CPU 旧版 0.0204/0.0227 秒、新版 0.0221 秒，峰值约 11 MiB，处于相同量级；不宣称 watcher CPU 进一步下降。

## 安装与本机验收

已从干净且已推送至 origin/main 的 `d93f3f67f3ca03d978f6f7d84edde3db3eea1acd` 构建，原路径 `.build/MacEvery.app` 运行，设置显示 `0.1.3-gd93f3f6`。深度/严格 ad-hoc 签名校验通过，去除签名后的 Rust 载荷 SHA 与最终实测制品相同。

旧 App 保留于 `.build/MacEvery.rollback-20261018-before-round3.app` 和本轮证据目录的 `original-app-before-install.app`。最新真实索引使用只读 online backup 保存为 `.build/performance-round3-20261018/live-index-before.sqlite`，7,297,578 条、quick_check=ok、SHA256 `5a4f6ba128e381d3e31f0c894b922cfded0533c86f4cb71b4445f9fd33738997`。备份成功后，首次只读验证因 WAL-header 副本无 sidecar 未能打开，改为仅对已冻结副本使用 immutable=1 验证；从未对 live DB 使用 immutable。原失败记录保留。

先正常退出旧 GUI；界面读取重新唤起旧 App 一次，替换前检查发现新 PID 并拦住覆盖。重新核对精确 bundle 路径后仅结束这些 MacEvery 进程，确认全部退出，再原位换入候选包。最终 GUI/service/watch PID 为 76429/76436/76437，父子归属正确。

原生窗口和真实 watcher 联合验收通过：新建 18 bytes → 修改 35 bytes → 重命名后仅新路径一条 → 删除后 0/No Results；各步另用精确路径只读 SQL 核对，文件/目录和查询已清理。设置 Fastest、Command-Shift-Space 与 roots/excludes 保持原值；数据库 ID 与备份相同，新日志迁移已启用且行数在保留上限内。没有重建真实索引，没有授予或更改系统权限；新包权限探测显示 Unknown（旧包为 Limited），本轮验收范围为原有索引及上述可访问目录，未扩大受保护目录覆盖。

App 空闲短观察使用同一工具、相同 20 秒采样方法。旧版平均 CPU 合计 0.122%/RSS 合计 2.660 GiB，新版 0.166%/2.618 GiB；100%=一个核。其他用户后台任务保留，观察前活动不同，不能据此宣称 idle CPU 改善或退化、也不能把 RSS 小幅下降当作本轮稳定收益。受控固定查询的内存结论是基本持平。
